# HMB bench-001: предложение по дизайну бенчмарка

> Статус: черновик (ветка `bench-001`). Цель — согласовать подход, затем зафиксировать формат задач и runner v0.

## 1. Что измеряем

HMB — Harness–Model Benchmark: оцениваем связку «harness + модель» на практических задачах трёх типов. Harness-цель — конкретный способ запуска агента: CLI в headless-режиме, расширение VSCode (зафиксированной версии) и т.п.; сравнение harness-целей при одной модели — часть результатов бенчмарка.

| Категория | Примеры задач | Способ проверки |
|---|---|---|
| `code` | реализовать функцию, починить баг, отрефакторить | unit-тесты (pytest) |
| `terminal` | разобрать логи, собрать проект, файловые и git-операции | конечное состояние файловой системы / репозитория |
| `excel` | сводная таблица, ВПР, очистка данных, отчёт | чтение итогового .xlsx (openpyxl после пересчёта) |

Принципы:

1. **Проверяем результат, а не процесс.** Verifier смотрит только на конечное состояние workspace, никакой оценки «по шагам».
2. **Полная автоматизация.** Задача = промпт + стартовое окружение + verifier + метаданные. Ручной проверки нет.
3. **Детерминизм.** Фиксированные входные данные (генераторы с сидом), зафиксированные версии инструментов, таймауты на задачу.
4. **Санити.** Каждая задача обязана проходить эталонным решением с score = 1.0 — иначе она не попадает в набор.
5. **Изоляция.** Задача выполняется в чистом окружении (Docker-контейнер; для v0 — чистая tmp-папка), агент не видит остальную машину.

## 2. Структура репозитория

```
hmb/
  tasks/
    code/
      code-001-.../
        task.yaml          # промпт, ограничения, метаданные
        env/               # стартовое состояние workspace
        verify/            # verifier: печатает "SCORE: <доля>", код 0 = verifier исправен
        solution/          # эталонное решение (для санити-прогона)
    terminal/
      term-001-.../
    excel/
      xls-001-.../
  hmb_runner/              # CLI ручного режима: list / start / verify / sanity / snapshot
  suites/
    core.yaml              # набор задач для базового прогона
  results/                 # журнал прогонов (journal.xlsx), в .gitignore
  workspaces/              # рабочие папки прогонов, в .gitignore
  report/                  # (v1+) генератор markdown-отчёта
```

## 3. Формат задачи: `task.yaml`

```yaml
id: code-001-fizzbuzz
category: code
difficulty: easy            # easy | medium | hard
time_limit_min: 10
prompt: |
  Реализуй функцию `fizzbuzz(n)` в src/fizzbuzz.py ...
verify:
  cmd: pytest verify/ -q
  scoring: tests            # tests = доля прошедших тестов; checks = доля пройденных проверок; binary = 0/1
tags: [python, spec]
```

Ход прогона одной задачи:

1. Runner разворачивает `env/` в чистый workspace.
2. Отдаёт агенту `prompt` (headless-режим harness'а или прямой API-цикл).
3. По завершении агента или по таймауту — стоп; workspace сохраняется как артефакт.
4. Verifier запускается на чистой копии workspace, чтобы агент не мог повлиять на проверку.
5. Результат пишется в `results/<run_id>/<task_id>.json`.

## 4. Категории задач

### 4.1 code

Типы: реализация по спецификации; багфикс (дан проект с падающими тестами); рефакторинг с сохранением поведения; маленький алгоритм; добавление фичи в мини-проект.

Verifier — pytest. Балл = доля прошедших тестов (или бинарно).

Пример: `code-003-json-flatten` — реализовать `flatten_json` по докстрингу; 12 тестов, включая краевые случаи.

### 4.2 terminal

Типы: анализ логов (grep/awk/jq → ответ в файл); сборка и починка проекта (make, npm); файловые операции (найти дубликаты, массовое переименование); git-операции (найти коммит-виновник, применить патч); служебные сценарии — только внутри контейнера.

Verifier — скрипт, проверяющий конечное состояние: наличие и содержимое файлов, код выхода сборки, состояние git. Стартовое окружение — фиксированный сгенерированный набор данных (логи с сидом).

Пример: `term-002-log-report` — в access.log на ~50k строк найти топ-10 IP по ошибкам 5xx и записать в report.txt в заданном формате.

### 4.3 excel

Ключевой нюанс — формулы против значений: если агент пишет .xlsx кодом (openpyxl), кэша вычисленных значений в файле нет. Решение: verifier пересчитывает книгу headless LibreOffice (`soffice --headless --convert-to xlsx`) и проверяет значения; наличие формул проверяется отдельно, если задача их явно требует.

Типы: сводная/агрегация; ВПР и склейка таблиц; очистка данных (дубликаты, даты, форматы); отчёт на нескольких листах; график (проверяется наличие chart и его серий).

Verifier — python + openpyxl/pandas: значения ячеек, структура листов, диапазоны, заливки, chart.

Пример: `xls-001-sales-pivot` — из orders.xlsx построить сводную по регионам и месяцам на листе Summary; verifier проверяет точные значения после пересчёта.

Входные данные не хранятся в git, а генерируются скриптом с сидом (`env/gen_data.py`) — репозиторий не разбухает, данные воспроизводимы.

## 5. Runner и режимы прогона

```
python -m hmb_runner run --suite suites/core.yaml --harness ext-1-2-3 --runs 3
```

- На задачу фиксируем: score, pass/fail, время, число шагов, токены, стоимость, лог сессии.
- Несколько прогонов на задачу (по умолчанию 3) — защита от случайности; итог — медиана или доля pass@1.
- Пока автоматического runner'а нет — работает ручной режим (5.1) с тем же форматом результатов.

### 5.1 Ручной режим: прогон из текущего окна VSCode (приоритет №1)

Задачи гоняются руками в уже открытой панели Claude Code; автоматической остаётся только проверка результата. Реализовано в CLI `hmb_runner` (v0):

- `python -m hmb_runner list` — список задач.
- `python -m hmb_runner start <task-id>` — разворачивает чистый workspace из `env/` задачи, снимает версии (5.4) и печатает промпт для вставки в панель.
- Агент работает в панели; по завершении `python -m hmb_runner verify <task-id>` запускает verifier на workspace и дописывает результат строкой в `results/journal.xlsx` (`--no-record` — проверить без записи; `--notes`, `--model` — метаданные прогона).
- `python -m hmb_runner sanity --all` — verifier на эталонных решениях: score каждой задачи обязан быть 1.0.
- Метрики в ручном режиме: время считается от `start`; токены и стоимость — `/cost` в сессии; полный транскрипт остаётся в `~/.claude/projects/...`.

Формат записи журнала — тот же, что у будущего автоматического прогона, поэтому ручные результаты останутся сравнимыми с автоматическими.

### 5.2 Harness-цели (`harnesses.yaml`)

Одна запись = одна зафиксированная связка; ключи и токены — вне git.

```yaml
harnesses:
  cli-opus-5:                    # вариант 1: CLI в headless-режиме
    type: cli
    cli_version: "x.y.z"        # закреплённая установка; автообновление выключено (DISABLE_AUTOUPDATER=1)
    model: claude-opus-5
    launch: claude -p --output-format stream-json --max-turns 40

  ext-1-2-3-opus-5:              # вариант 2: расширение VSCode (номер в имени = версия расширения, пример)
    type: vscode-extension
    extension_id: anthropic.claude-code
    extension_version: "1.2.3"
    vscode_version: "x.y.z"      # версия хоста тоже фиксируется
    model: claude-opus-5
```

### 5.3 Версии расширения: варианты запуска (приоритет №2)

Ограничение VSCode: в одном окне активна ровно одна версия расширения — сравнение версий всегда последовательное, окно за окном. Кроме ручной переустановки (п. 1) есть варианты:

1. **Профили — по профилю на версию.** Наборы расширений у профилей независимы: в `hmb-1.2.3` и `hmb-1.2.4` стоят свои версии. Запуск: `code --profile hmb-1.2.3 <workspace>`. Не забыть выключить автообновление глобально (`extensions.autoUpdate: false`), иначе оно обновит версии сразу во всех профилях.
2. **Отдельные каталоги расширений — самый скриптуемый вариант.** На версию — своя пара каталогов: `code --extensions-dir D:\hmb\ext\1.2.3 --user-data-dir D:\hmb\udata\1.2.3 <workspace>`; в каталоге расширений заранее установлен нужный `.vsix`. Запуск конкретной версии — одна команда; несколько окон могут работать параллельно (но измерения лучше вести последовательно).
3. **Portable-копии VSCode.** Каталог `data/` рядом с исполняемым файлом превращает установку в переносимую: свои расширения, настройки, кэш. N копий = N версий; максимальная изоляция, самая тяжёлая по диску.
4. (Ускоритель для ручного режима) **«Install Another Version…»** в меню расширения в панели Extensions — откат на любую marketplace-версию без поиска `.vsix`; годится для разовых прогонов, не для воспроизводимой серии.

Общее для всех вариантов: `.vsix` нужных версий берём из «Version History» на странице расширения в marketplace; автообновление расширений выключено; фиксируем версию не только расширения, но и CLI-ядра, которое оно использует — встроенное или из PATH (выясняется в v0).

### 5.4 Фиксация версий и снимок прогона

- Точная версия ставится из заранее скачанного `.vsix`: `code --install-extension path\to\claude-code-1.2.3.vsix`.
- **Снимок версий в каждом результате**: перед прогоном собираем фактические `extension / vscode / cli / model` (`code --list-extensions --show-versions`, `code --version`, `claude --version`) и пишем в результат; расхождение с манифестом (`harnesses.yaml`) помечает прогон невалидным. В ручном режиме снимок фиксирует `hmb record` или человек руками.

### 5.5 Автоматический прогон через расширение (v2)

Runner сам поднимает VSCode с нужной версией (вариант 2 из 5.3) на workspace задачи, программно подаёт промпт в панель расширения и ждёт завершения сессии. Механика подачи — исследовательская задача: (а) какие команды/URI-обработчики экспортирует расширение; (б) если прямого входа нет — UI-автоматизация. Транскрипт сессии (шаги, токены) берём из `~/.claude/projects/...` — метрики считаются так же, как для CLI.

Прогон через расширение идёт на хосте (GUI), изоляция слабее, чем у CLI в контейнере. Компромиссы: выделенная VM или учётная запись под прогоны либо смягчённые требования к изоляции.

## 6. Метрики и отчёт

- На задачу: score ∈ [0,1], pass (score = 1), время, токены, стоимость.
- По набору: pass@1 по категориям и уровням сложности, медианное время, средняя стоимость задачи.
- Сравнение harness-целей: одна suite на `cli` и `vscode-extension` при одинаковой модели показывает вклад harness'а отдельно от модели.
- `report/build.py` → `report.md`: таблица «задачи × агенты», агрегаты, ссылки на логи упавших прогонов.

## 7. Порядок работ

1. **v0 (ручной smoke):** по 1 задаче на категорию, ручной прогон из текущего окна (5.1), снимок версий, ручной журнал результатов.
2. **v1:** 15 задач (5 × 3 категории), три уровня сложности, частичный скоринг; серия прогонов на 3–5 версиях расширения через отдельные каталоги расширений (5.3.2); отчёт с агрегатами.
3. **v2:** автоматизация запуска (5.5), Docker-изоляция для CLI-цели, pass@k, несколько моделей, графики в отчёте.

- Изоляция на Windows: Docker Desktop / WSL2 vs tmp-папки для v0?
- Частичный скоринг или бинарный для terminal и excel?
- Включать ли длинные многошаговые задачи (30+ минут) в первый набор?
- Язык промптов: ru или en (влияет на сравнимость моделей между собой и с чужими бенчмарками)?
- Как программно подать промпт в панель расширения VSCode: экспортируемые команды/URI-обработчики или UI-автоматизация? Проверить до v1.
- Отдаёт ли прогон через расширение метрики сессии (токены, шаги) в том же виде, что CLI в stream-json?
